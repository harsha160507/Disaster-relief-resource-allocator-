# Phase 4: shipment workflows

Shipments connect reserved allocations to physical dispatch and confirmed delivery.
Each manifest contains 1–100 distinct allocations, all for the same destination.
Stock may come from multiple locations in that destination's organization.
Allocations can belong to multiple requests sharing that destination.

## Stock and request accounting

| Operation | Physical stock | Reserved stock | Item allocated | Item delivered |
| --- | --- | --- | --- | --- |
| Reserve quantity q | unchanged | +q | +q | unchanged |
| Create shipment | unchanged | unchanged | unchanged | unchanged |
| Dispatch shipment | -q | -q | unchanged | unchanged |
| Confirm delivery | unchanged | unchanged | unchanged | +q |
| Cancel before dispatch | unchanged | -q | -q | unchanged |

Available stock remains physical quantity minus reserved quantity. Dispatch
reduces both physical and reserved stock once, so availability does not increase.
Delivery never deducts stock again. Allocated quantity includes commitments that
are reserved, in transit or delivered. Cancelled allocations are excluded by
releasing their item quantity; the cancelled records remain in history.

For example, receiving 50 litres and reserving 20 leaves 30 available. Dispatch
leaves 30 physical and zero reserved; delivery leaves those same stock balances.
Cancelling before dispatch instead leaves 50 physical and zero reserved.

Request progress is calculated across all items:

- APPROVED: no active allocation or delivery.
- PARTIALLY_FULFILLED: some allocation, with unmet requested quantity.
- FULFILLED: all requested quantities allocated; goods may still await delivery.
- PARTIALLY_DELIVERED: some goods delivered, with requested delivery still incomplete.
- DELIVERED: every item's requested quantity delivered.

Existing FULFILLED allocation behavior remains compatible with previous phases.
The new deliveredQuantity in each request item and delivery states distinguish
actual delivery. A partially delivered request can receive further allocations
for its remaining unallocated quantity. Cancelling another pending shipment
preserves goods already delivered.

## Shipment states and manifest rules

Creating a shipment changes its allocations from RESERVED to CONFIRMED.
Dispatch changes the shipment and allocations to DISPATCHED; delivery changes
them to DELIVERED. Cancellation changes a CREATED shipment and its allocations
to CANCELLED and releases their reservations.

| Current state | Allowed actions |
| --- | --- |
| CREATED | Dispatch or cancel |
| DISPATCHED | Confirm delivery |
| DELIVERED / CANCELLED | Read history |

A reserved allocation can enter one manifest only. It must match the exact
destination, have stock in the same organization and belong to an approved,
allocated or partially delivered request. Allocations cannot be reassigned after
confirmation or cancellation. Reallocate released demand to create new records.

Tracking references are trimmed, nonblank, at most 255 characters and unique
with case-sensitive comparison. Manifests are fixed after creation. To change a
pending manifest, cancel it and create new allocations and a replacement.
Split deliveries use separate allocations/shipments; each action processes its
whole manifest.

Dispatch and delivery times are generated by the server. Delivery cannot precede
dispatch. Repeated or incompatible transitions return 422 without changing stock
or adding a success audit event. After a lost response, read the shipment before
retrying. Cancellation is restricted to CREATED because dispatched goods have
left warehouse inventory. Returns, losses and post-dispatch reconciliation
require a separate workflow. Legacy FAILED shipment records remain readable.

## Access and API

Authentication uses the issuer-bound local profiles configured in Phase 2.

| Role | Read own organization | Create / dispatch / cancel | Confirm delivery |
| --- | --- | --- | --- |
| SYSTEM_ADMIN | Across organizations | Yes | Yes |
| INVENTORY_MANAGER / DISASTER_COORDINATOR | Yes | Yes | Yes |
| FIELD_AGENT | Yes | No | Yes |
| PARTNER_MANAGER / VIEWER | Yes | No | No |

All HTTP access enforces organization boundaries, including manifest allocations,
destination filters and explicitly requested organizations. Existing organization
deactivation rules also apply. Roles supplied in JWT claims do not grant rights.

```text
POST /api/v1/shipments
GET  /api/v1/shipments/{id}
GET  /api/v1/shipments
POST /api/v1/shipments/{id}/dispatch
POST /api/v1/shipments/{id}/deliver
POST /api/v1/shipments/{id}/cancel
```

Create body:

```json
{
  "destinationId": "<location-uuid>",
  "trackingReference": "<unique-reference>",
  "allocationIds": ["<reserved-allocation-uuid>"]
}
```

Create returns 201 with the manifest. Transition requests have no body and return
the updated manifest. Responses include the shipment UUID, destination, status,
tracking reference, server timestamps, version and allocations.

Lists contain summaries in content, page, size, totalElements and totalPages.
Defaults are page 0, size 20; page must be 0–100000 and size 1–100. Optional
filters are status, destinationId and organizationId. Results sort by createdAt
descending, then UUID descending. Organization members automatically receive
their own scope; administrators can query all organizations or select one.

Malformed input returns 400, duplicate tracking references 409, business/state
violations 422, missing records 404, unauthenticated calls 401 and denied access
403. There are no shipment deletion or arbitrary status-update endpoints.

## Transactions, concurrency and audit

A transition locks its shipment, related requests, allocations and affected
inventory in a consistent order. Allocation also locks the request first and
acquires candidate inventory in global UUID order. Entity versions provide
additional conflict detection. Competing actions serialize or reject rather than
applying the same quantity twice.

Shipment, allocation, inventory, item and request audit changes share the business
transaction. A failed append rolls back the whole operation. Records capture
before/after quantities and statuses, related UUIDs and the trusted actor.
Tracking references are excluded from audit details. Administrators can filter
audit history by SHIPMENT or RESOURCE_REQUEST_ITEM in addition to earlier types.

These guarantees apply to application workflows. Direct SQL/repository edits and
external integrations must follow the same invariants and locking protocol.

## Migration and verification

V7 adds versions for shipments, allocations and requests, delivered quantities,
delivery request states and database checks. Previous migrations are unchanged.
Existing DELIVERED allocations initialize item delivery totals and progress;
stock balances are preserved without a second deduction. Review legacy shipment
balances before deployment. A delivered total exceeding an item's allocated
quantity fails migration for explicit reconciliation.

Shipment timestamp and allocation-link checks are added NOT VALID to preserve
pre-existing legacy rows; PostgreSQL enforces them on new or updated rows.
Reconcile old inconsistencies before validating those constraints. Legacy
shipments with missing timestamps, incompatible allocations or more than 100
allocations require review before workflow actions.

Run the normal tests and the dedicated PostgreSQL verification described in
[database setup](database-setup.md). PostgreSQL checks exercise simultaneous
manifest assignment, duplicate dispatch/delivery, dispatch versus cancellation,
allocation during dispatch, audit-failure rollback, restart persistence and
V6 delivery-data upgrade.
